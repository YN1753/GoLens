内存分配与逃逸分析

编译器做逃逸分析：值若必须在函数返回后仍可见，通常分配到堆并交给 GC； 否则可留在栈上，随返回自动回收。栈更快，但不是能逃就一定慢到不可接受。

栈与堆（心智模型）

  • 栈：每个 goroutine 有自己的栈，分配/回收几乎无成本，栈会增长/分段。
  • 堆：全局分配器管理，生命周期由 GC 决定；逃逸对象多 → GC 压力大。

常见逃逸原因

  • 返回局部变量地址 / 指针被外部持有
  • 闭包捕获、在其他 goroutine 中使用
  • 发送到 channel、存进接口、map/slice 被传出
  • 变量大小不确定或过大（实现细节，面试说「可能」）
如何验证

go build -gcflags="-m" ./... 会打印逃逸结论。生产优化先测再改，勿过早恐慌式改指针。

常见追问

逃逸一定有害吗？

不一定。很多对象本来就该共享。只在 profile 证明分配热点时再优化。

值接收者 vs 指针接收者会影响逃逸吗？

会影响复制与是否产生额外指针，间接影响逃逸，但以编译器输出为准。

速查表

  • 栈随返回回收；堆交给 GC
  • 指针逃逸 / 闭包 / goroutine / interface 装箱常见
  • -gcflags=-m 查看结论；先测量再优化
