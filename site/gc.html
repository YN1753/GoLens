GC 三色标记与写屏障

Go 并发 GC 用三色区分「还没扫 / 待扫 / 已扫」， 用写屏障防止标记过程中 mutator 把指针改到「从黑对象到白对象」导致漏标； 标记开始与结束仍需要短 STW 收束。

三色是什么

  • 白：尚未确认可达，结束时仍是白则可回收（概念上）。
  • 灰：已知可达，但子指针还没扫完，工作队列里躺着。
  • 黑：已扫完，从它出发的引用已处理。

不变式（面试可背）：标记过程中不应存在从黑直接指向白的指针—— 否则黑已「扫完」，白可能被永久错过。写屏障就是用来在并发写指针时维持这条不变式。

根从哪来

栈上变量、全局变量、寄存器等「根集合」被标灰，再从灰扩展到堆对象。Lab 用几个根节点示意即可。

STW 在哪

典型叙事：标记启动 STW（开启屏障、准备根）→ 并发标记 → 标记终止 STW（收尾、关屏障）→ 并发清扫。目的不是「全程停世界」，而是让并发阶段的不变式可成立。

交互 Lab · 逐步染色

零基础怎么用：把 GC 想成「图书馆盘点」。先跟关卡走：从门口名单（根）出发，灰=待查、黑=已查清、白=还没人碰。 并发时有人乱挪书（改指针），写屏障就是「值班员强制记一笔」。

常见追问

为什么并发标记还需要写屏障？

因为 mutator 与 marker 同时跑。若黑对象新指向一个未被发现的白对象，而 barrier 不介入，对象可能被误判为垃圾。

Dijkstra 与 Yuasa 怎么选？

常见科普：Dijkstra 强调「插入时把目标标灰」；Yuasa 是删除屏障思路。现代 Go 用混合写屏障融合优势。Lab 只演示「插入时灰化」这一直觉。

三色结束后白色对象一定立刻回收吗？

教学模型是「白即可回收」；真实实现还有清扫、span 管理与并发清扫，不必在八股里展开到 mspan 字段。

速查表

  • 白=未确认；灰=可达待扫；黑=已扫
  • 不变式：避免「黑 → 白」指针被漏标
  • 根：栈 / 全局 / 寄存器 → 标灰后扩展
  • 写屏障：并发改指针时把相关对象拉回灰色工作
  • STW：标记开始与终止短暂停，保证收束
